Design:
RunTicketMiner to DataManager: RunTicketMiner serves as the central hub, utilizing a DataManager to handle backend logic like generating IDs and saving/loading data. 
User to Customer/Organizer/Admin: The User class functions as an abstract parent for Customer, Organizer, and Admin, utilizing Inheritance to allow child classes to access shared personal attributes like firstName, username, and userID.
Event and Venue Hierarchies: Similar to the User structure, the Event and Venue classes are abstract parent classes. Through inheritance, Concert, Sport, and Special extend Event , while Arena, Auditorium, Stadium, and OpenAir extend Venue. This keeps shared pricing, capacity, and scheduling logic centralized in the parent classes.
RunTicketMiner to Logger: The system utilizes a dependency relationship with the Logger class. RunTicketMiner calls the static logAction() method to track and record each action taken by a user during runtime.

Assumptions:
We assumed that file updates (writing the updated CSVs) will only occur when the user shuts down the program, rather than overwriting files dynamically after every single update or deletion.

We assumed the input files would not change.

We assumed only Customers and Organizers can self-register , and Admins can only be created  by another Admin.

We assumed that serarching by "name" refers to first and last name when searching for Users.

We assumed MM/DD/YYYY for the date field.

We assumed 12-hour format (e.g., 07:30 PM) for time field.

We assumed the ticket prices are stored as doubles, allowing decimal numbers.

We assumed no constraint enforcement for seating percentages.

We assumed the system should list the matches and prompt the user to pick one by ID when a search has mutliple results.
